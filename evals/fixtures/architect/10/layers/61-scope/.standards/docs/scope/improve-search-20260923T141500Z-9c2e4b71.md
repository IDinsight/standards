# Improve User Search

## Goal

People often cannot find colleagues in the directory: search only matches the
start of a name with exact capitalization and never matches email addresses,
and an empty search returns the whole directory. Search should find users by
any part of their name or email regardless of case, show the most likely
matches first, and keep responses bounded.

## Constraints

- `GET /users/search?q=<query>` remains the search endpoint, and existing
  clients keep reading matching users from `results` in the response body.
- The user list continues to come from `data/users.json`; no new storage or
  external service.

## Non-goals

- Fuzzy or typo-tolerant matching.
- Searching fields other than name and email.
- Paging beyond the first set of results.

## Work

### 1. Broader matching

**Intent:** Let people find a colleague from any remembered fragment of a
name or email address.

**Done when:**

- `AC-001`: A query matches a user when it appears anywhere in the user's name
  or email address, ignoring letter case.
- `AC-002`: Leading and trailing spaces in the query are ignored; a query that
  is empty after trimming is rejected with status 400 and an error message,
  and no users are returned.

**Depends on:** None

### 2. Ordering and limits

**Intent:** Put the most likely colleagues at the top and keep responses small.

**Done when:**

- `AC-003`: Users whose name starts with the query are listed before other
  matches; within each group users are ordered alphabetically by name,
  ignoring case.
- `AC-004`: A response lists at most 20 users and reports the total number of
  matching users.

**Depends on:** 1

## Assumptions

- The directory holds at most a few thousand users, so scanning the whole
  list per request remains acceptable.
