# Writing the usage guide

The usage guide is the first thing people open when they wire the admin tool
to this service, and usually the last thing anyone updates. These are the
habits that have kept it useful so far.

## Who reads it

Two groups read `docs/usage.md`. Administrators want to know what they are
allowed to do and what happens when they do it. Admin-tool developers want the
exact request, the exact response, and every way it can fail. A section that
serves only one of them is usually missing half its content.

## Write from the code, not from the plan

A guide written from a design document describes the service we meant to
build. Before writing a section, run the route in a test or read the handler,
and describe what it does today: the status code, the headers, the shape of
the body, and anything it leaves behind on disk. If the code and the plan
disagree, that is worth raising with whoever owns the code, not smoothing over
in prose.

## Examples

Every example should be something a reader can paste and get the documented
result from. Use the seed data: record 1 has a comma in its title and record 3
has double quotes, which makes them good examples whenever quoting matters.

## Errors

Keep one table of status codes and their meaning, and add rows rather than
scattering error notes through the sections. Name the role that is refused,
not just the code.

## Keep it short

One section per route, in the order a reader would use them. Link the README
for setup instead of repeating it.
