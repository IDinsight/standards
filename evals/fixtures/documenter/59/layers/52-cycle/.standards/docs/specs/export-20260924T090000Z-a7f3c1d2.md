# Technical Design

## Context

Endpoints are plain functions dispatched by `handle(method, url)` in
`src/routes.js`, returning `{ status, headers, body }`. Invoice objects are
mapped to JSON inside `src/routes.js`; `src/csv.js` builds the CSV export from
`listInvoices()`. `docs/conventions.md` is the project's reference for JSON
endpoint conventions.

## Decision

Add `GET /invoices/export.json?from=YYYY-MM-DD&to=YYYY-MM-DD` to `handle`.
Extract the invoice mapping into a shared serializer so the export cannot
drift from `GET /invoices`. Filter `listInvoices()` on `issuedAt`. Represent
the response and errors as `docs/conventions.md` prescribes.

## Acceptance Coverage

- `AC-001`: new export route in `src/routes.js` filtering invoices by issue date.
- `AC-002`: shared serializer in `src/serialize.js`, used by `GET /invoices`, `GET /invoices/{id}`, and the export.
- `AC-003`: parameter validation in the export route; failures return 400 with the conventions error body.
- `AC-004`: No architectural impact; the guide is Documenter-owned and documents the contract above.

## Components

- `src/serialize.js`: `serializeInvoice(invoice)`, the single JSON
  representation of an invoice.
- `src/routes.js`: dispatch, query parsing, and validation for the export
  route.

## Interfaces and Contracts

- Request: `from` and `to` are calendar dates in `YYYY-MM-DD` form; both are
  required.
- Response `200`: `{"invoices": [...]}` with serialized invoices ordered by
  `issued_at`.
- Response `400`: `{"error": "<message>"}`.

## Technical Acceptance Criteria

- `AC-002`: for any invoice, the export and `GET /invoices` produce identical objects.
- `AC-003`: a missing parameter, a value that is not a valid `YYYY-MM-DD` date, or `from` later than `to` yields 400 and no invoices.

## Build Plan

1. Extract `serializeInvoice` and switch the existing endpoints to it.
2. Add the export route with parameter validation and date filtering.
