# Tony's documentation preferences

- Address the reader as "you" and write steps in the imperative.
- Open each section with one sentence saying what the reader can do there.
- For every endpoint, show one concrete request and the response it really
  produces, using records that exist in the seed data.
- Prefer short bullet lists for options and parameters; keep tables for
  status-code references only.
- Name headers, file names, and parameters in code spans exactly as the
  service spells them.
- Avoid "simply", "just", and "easily".
- Wrap prose at 80 columns.
