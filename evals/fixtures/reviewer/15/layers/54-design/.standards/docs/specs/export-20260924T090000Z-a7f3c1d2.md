# Technical Design

## Context

The scope adds an unattended export that uploads one CSV file of every record
to the document archive on each run (AC-001), retries transient upload
failures (AC-002), and does not retry uploads the archive refuses (AC-003).
Operations starts the run every hour with `pnpm --filter export archive-export`
and alerts on a non-zero exit status. According to `.standards/CONTEXT.md`,
the project has no scripts, outbound network calls, or shared retry helpers
yet; Node 22's global `fetch` is available and no HTTP library is installed.
Seed titles contain a comma and double quotes.

## Decision

Add a script, `scripts/archive-export.ts`, registered as the `archive-export`
package script. It takes the records from the same store `createApp` builds,
serializes them with a new CSV module, and uploads the file through a small
HTTP archive client wrapped in a retry function. The client, the retry
function, and the job are separate modules so tests can inject `fetch`, a fake
client, a fixed clock, and a fake `sleep`.

## Acceptance Coverage

- `AC-001`: CSV format, file name, `runArchiveExport`, and the archive upload
  request (Interfaces and Contracts).
- `AC-002`: `isTransient` classification and the `uploadWithRetry` retry
  schedule (Interfaces and Contracts); the script exits with status 1 when the
  upload fails.
- `AC-003`: `isTransient` treats every other non-2xx status as permanent, and
  `uploadWithRetry` rethrows it without waiting; the script exits with status 1.

## Components

- `src/export/csv.ts` (new): `csvCell`, `toCsv`, `exportFileName`.
- `src/archive/client.ts` (new): `ArchiveError`, the `ArchiveClient` type, and
  `createHttpArchiveClient({ baseUrl, token, fetch? })`.
- `src/archive/retry.ts` (new): `isTransient(error)` and
  `uploadWithRetry(client, name, body, options)`.
- `src/archive/job.ts` (new): `runArchiveExport({ store, archive, now?, retry? })`.
- `scripts/archive-export.ts` (new): reads the environment, runs the job, and
  sets the exit status.

## Interfaces and Contracts

- Upload request: `PUT <ARCHIVE_URL>/exports/<file name>` (a trailing `/` on
  `ARCHIVE_URL` is ignored) with headers `authorization: Bearer <ARCHIVE_TOKEN>`
  and `content-type: text/csv; charset=utf-8`; the body is the CSV text. Any
  2xx response means the file is stored.
- `ArchiveError(message, status?)`: `status` is the archive's HTTP status, or
  undefined when `fetch` rejects and no response arrives.
- Transient failures: no response, 429, or any status from 500 to 599. Every
  other non-2xx status is permanent.
- Retry schedule: after a transient failure, wait and send the upload again.
  The first wait is 500 ms and each later wait doubles, capped at 30 s per
  wait. Waits go through an injectable `sleep(ms)` so tests do not wait. A
  permanent failure, or an error that is not an `ArchiveError`, is rethrown
  at once.
- CSV format: UTF-8 without a byte order mark. Header row
  `id,title,owner,status,createdAt`, then one row per record in
  `RecordStore.list()` order (ascending `id`). Every row, including the last,
  ends with CRLF. A field containing a comma, a double quote, CR, or LF is
  enclosed in double quotes with each inner double quote doubled (RFC 4180);
  other fields are written as they are.
- File name: `records-<YYYYMMDDTHHMMSSZ>.csv` from the UTC time the run starts.
- Script: `ARCHIVE_URL` and `ARCHIVE_TOKEN` are required; when either is
  missing it prints a message and exits with status 2. Each retry is logged to
  stderr with the attempt number and the wait. On success it prints one line
  with the file name and exits 0. When the upload fails it prints the
  archive's error and exits with status 1.

## Data and Control Flow

`scripts/archive-export.ts` builds the store with `createApp()`, then
`runArchiveExport` lists every record, serializes it with `toCsv`, names the
file with `exportFileName(now())`, and calls `uploadWithRetry`, which calls
`client.put` until it succeeds or a failure is rethrown. The script turns a
rethrown failure into exit status 1.

## Technical Acceptance Criteria

- `AC-001`: The uploaded body equals `toCsv` of every record in `id` order,
  under the file name for the run's UTC start time, sent with the request
  headers above.
- `AC-002`: After a transient failure the next attempt follows the scheduled
  wait; when the upload fails, the script reports the archive's error and exits
  with status 1.
- `AC-003`: A permanent failure is rethrown after the first attempt with no
  wait, and the script exits with status 1.

## Build Plan

1. CSV serialization and the file name.
2. Archive client and retry wrapper.
3. Job, script, and the package script entry.

## Risks and Follow-up

- Two runs in the same second upload the same file name; the archive keeps the
  later file. Accepted, since operations runs the export hourly.
- A 429 response may carry `Retry-After`; this design does not read it.
