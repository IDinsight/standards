### DEV-001 — Optional timeout on the shared transfer helper

`Status`: `DONE` `Depends On`: `NONE` `Acceptance`: `AC-001, AC-003`

**Goal**

Let a transfer give up after a given time while leaving untimed transfers
exactly as they are.

**Affected Area**

`src/io/transfer.js` (`transfer`, new `TransferTimeoutError`).

**Expected Outcome**

`transfer(source, destination, { timeoutMs })` rejects with
`TransferTimeoutError` when the pipeline has not finished in time, with both
streams torn down and the timer cleared once the transfer settles. Without a
positive `timeoutMs` it is the existing `pipeline` call.

**Self-Check**

- `npm test` in the project root at commit
  `${COMMIT:Add timeout to export transfers}` (clean tree, Node 22, offline):
  exit 0; 10 tests passed, 0 failed.
- Manual `node --input-type=module` run at that commit: `transfer` from a
  readable into a writable that never acknowledges its first write, with
  `timeoutMs: 50`, rejected with `TransferTimeoutError` after about 50 ms.
- Inspection: the untimed branch returns `pipeline(source, destination)`.

### DEV-002 — Export timeout with a 30-second default

`Status`: `DONE` `Depends On`: `DEV-001` `Acceptance`: `AC-001, AC-002`

**Goal**

Bound every export by a timeout the caller can set.

**Affected Area**

`src/export.js` (`exportRecords`, `DEFAULT_EXPORT_TIMEOUT_MS`, re-export of
`TransferTimeoutError`).

**Expected Outcome**

`exportRecords(store, destination, { timeoutMs })` passes its timeout,
30 000 ms by default, to `transfer` and otherwise writes the same CSV as
before.

**Self-Check**

- `npm test` at `${COMMIT:Add timeout to export transfers}`: exit 0; the
  three export tests, which now run under the default timeout, pass
  unchanged.
- Manual run at that commit: `exportRecords` to a stalled writable with
  `timeoutMs: 50` rejected with `TransferTimeoutError`; inspection shows
  `DEFAULT_EXPORT_TIMEOUT_MS` is `30_000` and is the parameter default.
