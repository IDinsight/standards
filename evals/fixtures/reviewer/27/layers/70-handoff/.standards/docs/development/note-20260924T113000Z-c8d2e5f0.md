## Build Steps

### DEV-001 — Optional internal note on tickets

`Status`: `DONE` `Depends On`: `NONE` `Acceptance`: `EXPEDITED_REQUEST`

**Goal**

Tickets carry an optional `note` that staff can set when creating or updating a
ticket, using the same `optionalText` rules already applied to `assignee`.

**Affected Area**

- `src/tickets.js`: `newTicket`, `updateTicket`, `internalView`.
- `src/api.js`, `src/service.js`, `src/fields.js`: unchanged. Create and update
  are already staff-only and respond with `internalView`; customers read
  through `publicView`.

**Expected Outcome**

- `note` is trimmed; missing, `null`, or blank becomes `null`; a non-string or
  more than 500 characters is rejected with `ValidationError`, which the
  existing routes return as status 400 without storing anything.
- `updateTicket` changes `note` only when the update body contains the key;
  `null` or a blank string clears it.
- `internalView` includes `note`; `publicView` is unchanged and never includes
  it.

**Self-Check**

Run in the project root with Node 22 on commit
`${COMMIT:Add internal note field to tickets}` with a clean working tree
(`src/tickets.js` blob `${BLOB:src/tickets.js}`).

1. `npm test` (runs `node --test test/tickets.test.js test/api.test.js`): exit
   0; 11 tests, 11 passed, 0 failed. Existing ticket, view, permission, and
   validation behavior is unchanged.
2. Targeted check of the note through the routes:

```sh
node --input-type=module -e "
import { TicketService } from './src/service.js';
import { createTicketRoute, getTicketRoute, updateTicketRoute } from './src/api.js';
const service = new TicketService();
const staff = { staff: true };
const show = (result) => console.log(JSON.stringify(result));
show(createTicketRoute(service, staff, { title: 'Printer offline', note: '  Called twice  ' }));
show(getTicketRoute(service, { staff: false }, 1));
show(updateTicketRoute(service, staff, 1, { status: 'pending' }));
show(updateTicketRoute(service, staff, 1, { note: '   ' }));
show(createTicketRoute(service, staff, { title: 'Long note', note: 'x'.repeat(501) }));
show(createTicketRoute(service, staff, { title: 'Bad note', note: 42 }));
show(createTicketRoute(service, staff, { title: 'Max note', note: 'x'.repeat(500) }).status);
"
```

Exit 0. Output:

```text
{"status":201,"body":{"id":1,"title":"Printer offline","priority":"normal","status":"open","assignee":null,"note":"Called twice"}}
{"status":200,"body":{"id":1,"title":"Printer offline","priority":"normal","status":"open"}}
{"status":200,"body":{"id":1,"title":"Printer offline","priority":"normal","status":"pending","assignee":null,"note":"Called twice"}}
{"status":200,"body":{"id":1,"title":"Printer offline","priority":"normal","status":"pending","assignee":null,"note":null}}
{"status":400,"body":{"error":"note: must be at most 500 characters"}}
{"status":400,"body":{"error":"note: must be a string"}}
201
```

The trimmed note appears only for staff, the public view is unchanged, an update
without `note` keeps it, a blank note clears it, and both invalid notes are
rejected before anything is stored (the 500-character note gets id 2).

Limitation: these are Developer self-checks. The existing suite does not
exercise `note` directly; the note behavior is evidenced by check 2.

**Implementation Notes**

The 500-character limit comes from the request. No stored data needs migrating:
`TicketService` keeps tickets in memory.
