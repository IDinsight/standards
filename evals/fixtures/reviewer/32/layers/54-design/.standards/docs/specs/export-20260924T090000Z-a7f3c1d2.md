# Technical Design

## Context

The scope bounds the export's memory use: exporting 200,000 records must keep
peak heap growth at or below 32 MB (AC-001). According to
`.standards/CONTEXT.md`, `buildCsv` in `src/export.ts` renders every row and
joins them into one string, so heap use grows with the record count, while
`RecordSource.page(offset, limit)` already lets callers read records in id
order one slice at a time.

## Decision

Render and hand out the CSV in batches. A generator
`csvChunks(source, batchSize)` yields the header and then one string per batch
of `batchSize` records (default 1,000) read through `source.page`.
`writeCsv(source, out, batchSize)` writes those chunks to a Node `Writable`,
waits for `drain` whenever `write` returns false, ends the stream, and
resolves with the byte count once the stream finishes. `buildCsv` stays for
small in-memory callers and is built from the same chunks, so the CSV content
does not change.

## Acceptance Coverage

- `AC-001`: batched rendering in `csvChunks` and backpressure in `writeCsv`
  keep at most one rendered batch in memory; the measurement defined under
  Interfaces and Contracts is how the bound is established.

## Components

- `src/export.ts`: `csvChunks`, `writeCsv`, and `buildCsv`.
- `bench/export-memory.ts` (new): the measurement harness for the bound, run
  with `npm run bench:export`.

## Interfaces and Contracts

- `csvChunks(source: RecordSource, batchSize = 1000): Generator<string>`: the
  header chunk first, then one chunk per `source.page(offset, batchSize)` call
  until `source.count()` records are rendered. A `batchSize` that is not a
  positive integer throws `RangeError`.
- `writeCsv(source: RecordSource, out: Writable, batchSize = 1000): Promise<number>`:
  writes every chunk to `out`, awaiting `drain` after a `write` that returns
  false, then ends `out` and resolves with the total UTF-8 byte count after
  `out` finishes. Errors from `out` reject the promise.
- `buildCsv(source: RecordSource): string`: the concatenation of
  `csvChunks(source)`; output identical to the current implementation.
- Measurement: `node --expose-gc bench/export-memory.ts` builds a
  `MemorySource` holding 200,000 synthetic records before measuring, forces
  garbage collection, takes `process.memoryUsage().heapUsed` as the baseline,
  runs `writeCsv` into a `Writable` that discards its input and samples
  `heapUsed` on every chunk and once after completion, and reports peak minus
  baseline in MB (1 MB = 1,048,576 bytes). It writes the result to
  `bench/results/export-memory.json` (ignored by git) and exits with status 1
  when the growth exceeds 32 MB.

## Data and Control Flow

`writeCsv` pulls one chunk at a time from `csvChunks`, which reads the next
page only after the previous chunk has been written; when the destination's
buffer is full, the loop pauses until `drain`.

## Technical Acceptance Criteria

- `AC-001`: On Node 22, the measurement above reports peak heap growth at or
  below 32 MB for 200,000 records.
- `AC-001`: `writeCsv` holds at most one rendered batch at a time and does not
  keep writing to a full `Writable` without waiting for `drain`.

## Build Plan

1. `csvChunks` and `writeCsv`; rebuild `buildCsv` on them.
2. Measurement harness and the `bench:export` script.

## Risks and Follow-up

- `heapUsed` excludes Buffer and other external memory held by the
  destination stream; the bound is defined on heap use, as the scope states.
- Heap figures vary between runs; a run above the budget counts as failing.

## Alternatives

- `Readable.from(csvChunks(...))` with `pipeline`: equivalent memory
  behavior; the explicit loop keeps the byte count and error path simple.
