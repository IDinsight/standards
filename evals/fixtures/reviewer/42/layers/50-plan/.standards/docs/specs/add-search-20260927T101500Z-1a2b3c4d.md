# Technical Design

## Context

`src/handlers.js` routes every request; `src/records.js` implements
`GET /records` with the paging rules in docs/api.md ("Paging"). The store is
in memory and small, so a linear scan is acceptable.

## Decision

Add `src/search.js` exporting `searchRecords(store, params)`, routed from
`handle` at `/records/search`. Matching is a case-insensitive substring test
on `name` and `email` over `store.all()`, preserving store order. Paging uses
exactly the rules `GET /records` uses.

## Acceptance Coverage

- `AC-001`, `AC-002`: `searchRecords` trims and lowercases `q` and each
  record's `name` and `email`; a record matches when either field contains
  `q`.
- `AC-003`: `searchRecords` returns `{ status: 400, body: { error } }` when
  `q` is missing or blank after trimming, before reading the store.
- `AC-004`: paging from `page` and `pageSize` under the docs/api.md rules;
  the body is `{ items, page, pageSize, total }`, with `total` counting all
  matches.

## Interfaces and Contracts

- `GET /records/search?q=&page=&pageSize=` returns 200 with
  `{ items, page, pageSize, total }` or 400 with `{ error }`. Items are
  `{ id, name, email }`.
- `page`: integer, at least 1, default 1.
- `pageSize`: default 20; values above 50 are treated as 50; values below 1
  are treated as 1. The response `pageSize` is the size applied.

## Technical Acceptance Criteria

- `AC-004`: For a `pageSize` greater than 50, the response `pageSize` is 50 and
  `items` holds at most 50 records.
- `AC-004`: Without `pageSize`, the response `pageSize` is 20.

## Build Plan

1. Matching and `q` validation in `src/search.js`.
2. Paging of the matched records.
3. Route `/records/search` in `src/handlers.js`.
