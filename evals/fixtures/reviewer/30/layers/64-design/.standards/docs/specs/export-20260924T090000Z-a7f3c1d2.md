# Technical Design

## Context

The scope adds export runs: each run exports every invoice not yet exported as
CSV and records them as exported (AC-001), and a failed run changes nothing
(AC-002). According to `.standards/CONTEXT.md`, invoices live in a libSQL
server reached through `src/db/client.js`, whose `transaction(work)` runs
`BEGIN IMMEDIATE`, the work, and `COMMIT` or `ROLLBACK` on one server stream;
SQL lives in repository modules; schema changes are numbered migrations.

## Decision

Record each run in a new `export_runs` table and point exported invoices at
their run through a nullable `invoices.export_run_id`. `runExport(db)` does
the whole run in one `db.transaction()`: select pending invoices, insert the
run, mark each invoice, and build the CSV from the selected rows. Relying on
the database transaction, rather than compensating writes, keeps a failed run
from leaving partial changes. `BEGIN IMMEDIATE` takes the write lock at the
start, so overlapping runs are serialized; the conditional update still
rejects an invoice another run has marked.

## Acceptance Coverage

- `AC-001`: migration `002_export_runs.sql`; `pendingInvoices`, `insertRun`,
  and `markExported` in `src/exports/repository.js`; the CSV format in
  `src/exports/csv.js`; `runExport` in `src/exports/service.js`.
- `AC-002`: one transaction per run through `connect().transaction()`, with
  `ROLLBACK` on any error, including the conflict check in `markExported`.

## Components

- `migrations/002_export_runs.sql` (new): the `export_runs` table and the
  `invoices.export_run_id` column.
- `src/exports/repository.js` (new): the export SQL and `ExportConflictError`.
- `src/exports/csv.js` (new): `formatAmount` and `toCsv`.
- `src/exports/service.js` (new): `runExport(db, { now })`.
- `src/db/client.js`: used as it is.

## Interfaces and Contracts

- Schema: `export_runs (id INTEGER PRIMARY KEY, created_at TEXT NOT NULL,
  invoice_count INTEGER NOT NULL)`; `invoices.export_run_id INTEGER
  REFERENCES export_runs (id)`, `NULL` until the invoice is exported.
- `runExport(db, { now })`: returns `null` when no invoice is pending,
  otherwise `{ runId, invoiceCount, csv }`. On any failure it rethrows the
  error after the transaction is rolled back. `created_at` is `now()` as an
  ISO 8601 UTC string.
- CSV: header `invoice_id,customer,amount,issued_on`; one row per exported
  invoice in ascending id; `amount` is `amount_cents` in currency units with
  two decimals; RFC 4180 quoting for fields containing a comma, double quote,
  CR, or LF; every row ends with CRLF.
- Marking: `UPDATE invoices SET export_run_id = ? WHERE id = ? AND
  export_run_id IS NULL`; an update that changes no row throws
  `ExportConflictError`, which rolls the run back.

## Data and Control Flow

`BEGIN IMMEDIATE`, then select invoices with `export_run_id IS NULL` ordered
by id; if there are none, commit and return `null`. Otherwise insert the
`export_runs` row, update each invoice, `COMMIT`, and return the CSV built
from the selected rows. Any error before `COMMIT` leads to `ROLLBACK` on the
same stream and is rethrown to the caller.

## Technical Acceptance Criteria

- `AC-001`: A run includes exactly the invoices whose `export_run_id` is NULL
  when the run starts, in id order, sets their `export_run_id` to the new
  run's id, and returns CSV rows for exactly those invoices.
- `AC-001`: A run that starts after another run has committed includes only
  invoices recorded since.
- `AC-002`: All statements of a run execute in one libSQL transaction; when
  any statement or the conflict check fails, the transaction is rolled back,
  and afterwards the database holds no `export_runs` row for that run and no
  invoice whose `export_run_id` was set by it.

## Risks and Follow-up

- The guarantee depends on every statement of a run reaching the server on the
  transaction's stream; a statement issued through `db.execute` instead of the
  `tx` handle would run outside it.
- Deleting invoices is not supported today; if it is added, run counts may no
  longer match the invoices that point at a run.

## Alternatives

- Inserting the run and marking invoices in separate requests with cleanup on
  failure: rejected because a crash between steps would leave partial changes.
