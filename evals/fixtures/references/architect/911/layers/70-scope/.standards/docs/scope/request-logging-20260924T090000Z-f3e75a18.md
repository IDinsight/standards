# Structured Request Logging

## Goal

Operators cannot follow a single request through the service today: the only
log output is a few ad hoc `print()` messages, with no status, timing, or
correlation identifier. Give every request a consistent, machine-readable log
record that can be matched with the caller's own records, and make sure
credentials never reach the logs.

## Constraints

- Logs continue to go to the container's standard output, which the hosting
  platform already collects.
- Existing routes, request and response bodies, and status codes stay as they
  are; the only response change is the request ID header in AC-002.
- The existing bearer-token check keeps its current behavior.

## Non-goals

- No database, schema, or migration change.
- Metrics, tracing, alerting, or an error tracking service.
- Changing the platform's log collection or retention.

## Work

### 1. Request log line and request ID

**Intent:** Each request can be found in the logs by one identifier, which the
caller can supply or read back. When the caller sends no `X-Request-ID`
header, the service assigns one.

**Done when:**

- `AC-001`: Every request produces one structured log line with the method,
  path, status, duration, and a request ID.
- `AC-002`: The request ID comes from the `X-Request-ID` header when the caller
  sends one and is returned in the response's `X-Request-ID` header.

**Depends on:** None

### 2. Credentials stay out of the logs

**Intent:** Log output can be shared with operators without exposing
credentials.

**Done when:**

- `AC-003`: Logs never contain passwords, tokens, or Authorization headers.

**Depends on:** Work item 1
