## Build Steps

### DEV-001 — Archive flag and archive route

`Status`: `DONE` `Depends On`: `NONE` `Acceptance`: `AC-001`

**Goal**

Records carry an archived flag, and the API can archive a record.

**Affected Area**

`src/store.js` (field on create, `archive(id)`), `src/handlers.js`
(`archiveRecord`), `src/routes.js` (`POST /records/:id/archive`).

**Expected Outcome**

New records have `archived` set to false. `POST /records/:id/archive` returns
200 with the archived record, or 404 for unknown or malformed ids.
`GET /records/:id` shows the flag.

**Self-Check**

Ran `node --test test/records.test.js` from the project root on the working
tree over ${COMMIT:Plan record archiving}, with `src/store.js`,
`src/handlers.js`, and `src/routes.js` changed. Exit 0: 5 passed, 0 failed.

Sanity run from the project root with `node --input-type=module` on the same
content: after creating one record, archiving id 1 returned 200 with the flag
set to true, and a read of id 1 returned 200 with the flag still true. Archiving
id 99 returned 404, and archiving id `abc` returned 404. The existing tests do
not exercise archiving; formal coverage is Tester's.

**Implementation Notes**

`RecordStore.list()` still returns every record, as the design requires.
DEV-002 filters in `listRecords`.

### DEV-002 — Hide archived records from the default list

`Status`: `IN_PROGRESS` `Depends On`: `DEV-001` `Acceptance`: `AC-002`

**Goal**

The default list leaves out archived records unless the caller asks for them.

**Affected Area**

`listRecords` in `src/handlers.js` only. `RecordStore.list()` stays unchanged
per the design.

**Expected Outcome**

`GET /records` omits archived records. With `includeArchived=true` it returns
them too. `q` filtering works in both cases.

**Self-Check**

Planned: `node --test test/records.test.js` from the project root, plus a
sanity run listing one archived and one active record with and without
`includeArchived=true`, combined with `q`. Not yet run.
