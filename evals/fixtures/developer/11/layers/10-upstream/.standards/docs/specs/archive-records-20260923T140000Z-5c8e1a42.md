# Technical Design

## Context

The records API is `route()` in `src/routes.js`. It dispatches to handlers in
`src/handlers.js` that return `{ status, body }`, backed by the in-memory
`RecordStore` in `src/store.js` (see `.standards/CONTEXT.md`).

## Decision

- Store an `archived` boolean on every record, set to `false` on create. Records
  are never removed by archiving.
- `RecordStore.archive(id)` sets the flag and returns a copy of the record, or
  `null` for an unknown id.
- Expose archiving as `POST /records/:id/archive`, handled by a new
  `archiveRecord` handler. It mirrors `getRecord`: 200 with the record, or 404
  `{ error: 'not found' }` for unknown or malformed ids.
- Filter in `listRecords`, not in the store. `RecordStore.list()` keeps
  returning every record.

## Acceptance Coverage

- `AC-001`: the `archived` field, `RecordStore.archive`, the `archiveRecord`
  handler, and the `POST /records/:id/archive` route. `getRecord` returns the
  stored flag unchanged.
- `AC-002`: the archived filter in `listRecords`, keyed on the
  `includeArchived` query parameter.

## Interfaces and Contracts

- `POST /records/:id/archive` (no body): 200 with the full record including
  `archived: true`. 404 with `{ error: 'not found' }` otherwise. Archiving an
  already archived record is a 200 no-op.
- `GET /records`: the query accepts `includeArchived`. Only the string value
  `true` includes archived records; any other value or its absence omits them.
  The `q` title filter applies in both cases.
- Every record body returned by any route carries `archived`.

## Technical Acceptance Criteria

- `AC-001`: after `POST /records/:id/archive`, `GET /records/:id` returns 200
  with `archived: true`, and the store still holds the record.
- `AC-002`: `listRecords` drops records with `archived: true` unless
  `query.includeArchived === 'true'`, and applies `q` to the remaining records.
