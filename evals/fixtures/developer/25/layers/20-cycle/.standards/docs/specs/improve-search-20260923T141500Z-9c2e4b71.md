# Technical Design

## Context

Search lives entirely in `searchUsers(users, query)` in `src/search.js`, which
the CLI calls. It trims the query, returns no results for a blank query, and
does a case-sensitive substring match on `name` only (see
`.standards/CONTEXT.md`).

## Decision

Keep the change inside `searchUsers`. Lowercase the trimmed query and each
candidate field with `String.prototype.toLowerCase()` (no locale-specific
folding), and treat a user as a match when either `name` or `email` contains
the query. Then order matches in two groups: name-prefix matches first, all
other matches after, each group in input order. No new modules or dependencies;
the CLI is unchanged.

## Acceptance Coverage

- `AC-001`: Lowercased substring match on `name` in `searchUsers`.
- `AC-002`: The same lowercased substring match applied to `email`; a user
  matches when either field matches.
- `AC-003`: Two-group ordering in `searchUsers`; the prefix test compares the
  lowercased `name` with the lowercased query.

## Interfaces and Contracts

- `searchUsers(users, query)` keeps its signature and returns the original user
  objects (no copies or added fields).
- A blank or whitespace-only query still returns an empty array.
- `src/cli.js` and its output format are unchanged.

## Technical Acceptance Criteria

- `AC-001`: `searchUsers(users, 'ada')` and `searchUsers(users, 'ADA')` return
  the same users as `searchUsers(users, 'Ada')`.
- `AC-002`: A query that appears only in a user's `email`, in any case, returns
  that user.
- `AC-003`: Every user whose lowercased name starts with the lowercased query
  precedes every other match, and relative input order is preserved within each
  group (two filtered passes, or a stable sort on a group key).

## Build Plan

1. Case-insensitive matching on name and email in `searchUsers`.
2. Prefix-first ordering on top of the new matching.

## Risks and Follow-up

- `toLowerCase()` does not fold every Unicode case variant; acceptable for the
  directory's data.
