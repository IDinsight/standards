# Technical Design

## Context

All API routing lives in the pure handler returned by `createApp` in
`src/app.js`; the page in `public/contacts.js` renders `GET /contacts`. The
store is in memory and small, so a linear scan per request is adequate.

## Decision

Add a dedicated `GET /contacts/search` route backed by a pure matcher module,
and have the page call that route rather than filtering in the browser, so the
API and the page share one matching rule.

## Acceptance Coverage

- `AC-001`: `GET /contacts/search` route in `createApp` (`src/app.js`), backed by `searchContacts(contacts, query)` in a new `src/search.js`.
- `AC-002`: search input in `public/contacts.html` wired in `public/contacts.js` to `GET /contacts/search`, falling back to `GET /contacts` when cleared.

## Components

- `src/search.js` — pure matcher; no store or HTTP knowledge.
- `src/app.js` — route registration, query validation, and response shape.
- `public/contacts.js` — input handling and re-rendering through the existing
  render function.

## Interfaces and Contracts

- `GET /contacts/search?q=<text>` returns 200 with a JSON array of contact
  objects in the same shape as `GET /contacts`, in store order. When `q` is
  missing, or blank after trimming, it returns 400 with
  `{ "error": "q is required" }`.
- Matching: trim `q` and lowercase it; a contact matches when its lowercased
  `name` or `email` contains it.
- `searchContacts(contacts, query)` returns a new array and does not mutate its
  input.

## Technical Acceptance Criteria

- `AC-001`: The search route does not change the responses of the existing `/contacts` routes, and uses the shared `json` helper for both outcomes.
- `AC-002`: The page waits about 250 ms after the last keystroke before requesting, and renders results with the same function used for the full list.

## Build Plan

1. Matcher and API route.
2. Page search box on top of the route.
