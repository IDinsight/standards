# Technical Design

## Context

The directory (`src/directory.js`) holds normalized `{ id, name, email }`
records with lowercase emails and exposes `list()` in insertion order.
Directories are small (hundreds of contacts), and the library has no
dependencies.

## Decision

Add `searchContacts(directory, query)` in a new module `src/search.js`,
exported from `src/index.js`. It scans `directory.list()` linearly; no index is
built, because directory sizes do not justify one and an index would have to
track later changes.

## Acceptance Coverage

- `AC-001`: `searchContacts` name matching under the matching rule below.
- `AC-002`: the same function also matches the stored email; a contact matching
  both fields is included once.
- `AC-003`: query normalization; an empty normalized query returns `[]`.

## Interfaces and Contracts

- `searchContacts(directory, query: string): Contact[]` — returns the contact
  objects from `directory.list()` that match, in directory order. It does not
  copy or modify contacts.

## Data and Control Flow

Matching rule: normalize the query by trimming surrounding whitespace and
lowercasing it. An empty result returns `[]` without scanning. Otherwise a
contact matches when its lowercased `name` contains the normalized query, or,
once email matching is added, when its stored (already lowercase) `email`
contains it. Each contact is tested once, so it appears at most once.

## Technical Acceptance Criteria

- `AC-001`: For a non-empty query, every contact whose lowercased name contains
  the normalized query is returned, and no other, in `list()` order.
- `AC-002`: A contact whose email contains the normalized query is returned even
  when its name does not; a contact matching both appears once.
- `AC-003`: `searchContacts(directory, '')` and a whitespace-only query return
  `[]`.

## Build Plan

1. Query normalization and name matching in `src/search.js`, with the export.
2. Email matching in the same function.
