# Case Summary Endpoint

## Goal

Caseworkers want a short summary of a case's notes, generated by the language
model the service already integrates with and stored with the case, so they can
review a case quickly.

## Constraints

- Use the existing provider integration and the existing `case_summaries`
  storage.
- Existing case routes keep their current behavior.

## Non-goals

- Listing, editing, or deleting summaries.
- Evaluating the quality or wording of generated summaries.
- Streaming responses or background generation.

## Work

### 1. Generate and store a case summary

**Intent:** Let the owner of a case request a summary and get it back once it
is stored, with clear outcomes when the provider cannot produce one.

**Done when:**

- `AC-001`: When the owner of a case requests its summary, the API responds 201
  with the stored summary.
- `AC-002`: When the provider rate-limits the request, the API responds 503
  with a `Retry-After` header and stores no summary.
- `AC-003`: When the model returns `record_summary` tool arguments that are not
  valid JSON, the API responds 502 and stores no summary.

**Depends on:** None
