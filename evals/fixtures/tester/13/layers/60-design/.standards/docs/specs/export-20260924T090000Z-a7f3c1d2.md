# Technical Design

## Context

`exportRecords` in `packages/export/src/export.js` currently calls
`listRecords` and writes the whole CSV with one `writeFile`.
`.standards/CONTEXT.md` records that `@records/db` runs one simple-protocol
query at a time, returns text values, offers no transaction helpers, and that
callers own the connection. The CSV format lives in
`packages/export/src/csv.js`.

## Decision

Keep the `exportRecords(db, filter, outputPath)` entry point and add an
options argument `{ batchSize }` (default 500). The export runs in one
transaction on the caller's connection: it records the export job, reads the
listing query through a server-side cursor in batches of `batchSize`, appends
each batch to a temporary file next to the output, and commits only after the
file is complete and in place. Any failure rolls the transaction back and
removes the temporary and final files. A cursor is used rather than
`LIMIT`/`OFFSET` paging so the export reads one consistent snapshot and does
not re-scan earlier rows.

## Acceptance Coverage

- `AC-001`: cursor-based batched reads inside one transaction, the
  `export_jobs` table with its insert and update, and the failure path (Data
  and Control Flow, Interfaces and Contracts).
- `AC-002`: rows are written with the existing `HEADER` and `recordLine` from
  `csv.js`; the format is unchanged.

## Components

- `db/schema.sql`: new `export_jobs` table.
- `packages/export/src/export.js`: `exportRecords` rewritten as below, and
  `DEFAULT_BATCH_SIZE`.
- `packages/export/src/records.js`: unchanged; `selectRecordsSql` and
  `toRecord` are reused so the export lists exactly what `listRecords` lists.

## Interfaces and Contracts

- `exportRecords(db, filter, outputPath, { batchSize = 500 } = {})` resolves
  with `{ jobId, path, rowCount }`. `batchSize` must be a positive integer
  (`RangeError` otherwise). An unknown `status` throws `RangeError` from
  `selectRecordsSql` before any statement is sent. `db` must be an idle
  connection outside a transaction.
- `export_jobs`: `id serial PRIMARY KEY`, `filter jsonb NOT NULL` (the filter
  as given, `{}` when none), `file_name text NOT NULL` (base name of
  `outputPath`), `row_count integer`, `started_at timestamptz NOT NULL
  DEFAULT now()`, `finished_at timestamptz`. A committed row always has
  `row_count` and `finished_at` set.
- Files: rows are appended to `<outputPath>.partial`, which is renamed to
  `outputPath` once closed. The output folder must already exist.

## Data and Control Flow

1. `BEGIN`.
2. `INSERT INTO export_jobs (filter, file_name) ... RETURNING id`.
3. `DECLARE export_cursor NO SCROLL CURSOR FOR` the `selectRecordsSql(filter)`
   query.
4. Open `<outputPath>.partial` and write `HEADER`.
5. Repeat `FETCH FORWARD <batchSize> FROM export_cursor`, appending each batch
   with `recordLine(toRecord(row))`, until a batch has fewer than
   `batchSize` rows. At most one batch is held in memory.
6. `CLOSE export_cursor`, then `UPDATE export_jobs` setting `row_count` and
   `finished_at`.
7. Close the file, rename it to `outputPath`, then `COMMIT`.

On any error after `BEGIN`: close the file if open, remove
`<outputPath>.partial` and, if already renamed, `outputPath`, issue
`ROLLBACK` (ignoring a failure to roll back on a broken connection), and
rethrow the original error.

## Technical Acceptance Criteria

- `AC-001`: the export never requests more than `batchSize` rows per round
  trip and never holds more than one batch; rows arrive in id order with the
  listing filters applied.
- `AC-001`: after a committed export, `export_jobs` has exactly one new row
  whose `row_count` equals the number of data lines in the file.
- `AC-001`: after a failure at any step before `COMMIT` completes, the
  database has no `export_jobs` row for the export and neither
  `<outputPath>.partial` nor `outputPath` exists.
- `AC-002`: the header and lines are byte-identical to what `csv.js`
  produces for the same records.

## Build Plan

1. `export_jobs` in `db/schema.sql`.
2. Streaming export in one transaction.
3. Failure path: rollback and file cleanup.

## Risks and Follow-up

- A process crash between the rename and `COMMIT` can leave a file without a
  job row. Accepted.
- The cursor keeps a snapshot and a transaction open for the duration of the
  export.

## Alternatives

- `LIMIT`/`OFFSET` paging: rejected; it re-scans earlier rows and can skip or
  repeat rows when records change during the export.
- Recording the job after the file is written, outside the transaction:
  rejected; a failure between the two leaves them inconsistent.
