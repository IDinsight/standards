# Streaming CSV Export with Export Jobs

## Goal

Exports of large record sets currently load every matching record into memory
before writing the file, and nothing records that an export happened. Exports
should stream from the database into the CSV file, each completed export
should be recorded, and a failed export should leave nothing behind.

## Constraints

- Exports use the same filters and validation as listing records
  (`listRecords`).
- The CSV format of existing exports does not change.
- PostgreSQL is the system of record; export bookkeeping lives in the same
  database.

## Non-goals

- Serving, downloading, or cleaning up export files.
- Formats other than CSV, and column selection.
- Retrying failed exports.

## Work

### 1. Streamed, all-or-nothing export

**Intent:** Keep memory use flat for large exports and make every export
either fully recorded or not recorded at all.

**Done when:**

- `AC-001`: An export of the filtered records reads them from the database in bounded batches, in id order, instead of loading the whole result at once; a completed export leaves the CSV file at the output path and one export job recording its filter, file name, and row count; if reading or writing fails partway, the export's database changes are rolled back so no export job remains, and neither a complete nor a partial CSV file is left behind.

**Depends on:** None

### 2. Unchanged file format

**Intent:** Spreadsheets and scripts that read existing exports keep working.

**Done when:**

- `AC-002`: Exported files keep the existing CSV format: the header `id,title,owner,status,createdAt`, one CRLF-terminated line per record, and RFC 4180 quoting of fields containing commas, double quotes, or line breaks.

**Depends on:** 1

## Assumptions

- Callers pass an idle connection that is not already inside a transaction.
