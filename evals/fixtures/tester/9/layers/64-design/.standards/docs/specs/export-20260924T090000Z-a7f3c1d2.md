# Technical Design

## Context

The scope adds a CSV export of the filtered records list (AC-001) whose
contents come from one point in time (AC-002). Listing already builds its
query in `list_query` (`app/repository.py`), and `iter_records`
(`app/streaming.py`) reads that query's rows in batches through a named
server-side cursor on a psycopg connection (`app/db.py`). There is no export
code and no command-line entry point.

## Decision

Add `app/export.py` with `write_csv` (formatting only) and `export_csv`
(snapshot and streaming), and an `export` command in a new `app/cli.py`.
`export_csv` opens one transaction, sets it to `REPEATABLE READ, READ ONLY`
before any row is read, and passes the rows from `iter_records` to
`write_csv`, so memory use stays bounded by the batch size and every row
comes from the transaction's snapshot. The standard library `csv` writer
provides RFC 4180 quoting.

## Acceptance Coverage

- `AC-001`: `export_csv` reads through `iter_records`, which uses `list_query`, so filters, ordering, and `parse_filter` validation match listing; `write_csv` defines the header, row format, and quoting.
- `AC-002`: one `REPEATABLE READ, READ ONLY` transaction around the whole export, set before the first row is read.

## Components

- `app/export.py` (new): `write_csv` and `export_csv`.
- `app/cli.py` (new): the `export` command.
- `app/streaming.py` (`iter_records`) and `app/repository.py` (`list_query`)
  are used unchanged.

## Interfaces and Contracts

- `write_csv(records, out) -> int`: header `id,title,owner,status,created_at`,
  then one row per record in the given order; `created_at` as ISO 8601 with
  its offset (`datetime.isoformat()`); every row, including the last, ends
  with CRLF; a field containing a comma, double quote, CR, or LF is enclosed
  in double quotes with embedded double quotes doubled, other fields are
  written as they are. Returns the number of records written.
- `export_csv(conn, record_filter, out, batch_size=500) -> int`: `conn` must
  not be in autocommit mode and must have no open transaction. The export
  runs in `conn.transaction()` whose first statement is
  `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ, READ ONLY`. Returns the
  number of records written; the transaction ends when the export finishes or
  raises.
- `python -m app.cli export [--status S] [--owner O] [--q TEXT]`: writes the
  CSV to standard output using `DATABASE_URL`. An invalid filter exits with
  status 2 and the `parse_filter` message before connecting.

## Data and Control Flow

`main` parses the filter with `parse_filter`, opens a connection with
`connect()`, and calls `export_csv`, which begins the transaction, sets its
mode, and lets `write_csv` pull rows from `iter_records`; the named cursor
fetches `batch_size` rows at a time inside the transaction. The transaction
ends after the last row is written, or rolls back if writing fails.

## Technical Acceptance Criteria

- `AC-001`: For any filter, the exported rows are the records `list_records` returns for it, in the same order, formatted and quoted as above.
- `AC-001`: Rows are read in batches of `batch_size` through the server-side cursor; the export does not load every matching row first.
- `AC-002`: Inserts, updates, and deletes committed by other sessions after the export's first read do not appear in its output.

## Build Plan

1. `write_csv`.
2. `export_csv` with the snapshot transaction.
3. The `export` command.

## Risks and Follow-up

- A long export keeps its snapshot open, which holds back vacuum of rows
  changed meanwhile. Acceptable at the current table size.

## Alternatives

- `COPY (SELECT ...) TO STDOUT WITH (FORMAT csv)`: rejected for now because
  it bypasses `write_csv`'s `created_at` formatting and the existing
  `iter_records` path.
